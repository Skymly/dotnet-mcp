# DotNetMCP 5.0 release latency verification

Compared the last published 4.x release (`v4.0.1`, `13894f5`) with
`v5.0.0` (`33935fb`) on the same Windows 10.0.26300 host, with .NET SDK
10.0.303, runtime 10.0.15, and Release builds. The 5.0.0 harness added the
two new symbol scenarios in this change. Product code came from the tags.

Both releases used clean tracked-source exports with the same subject
revisions and no carried-over subject restore or build outputs. Runs used
one warm-up and five measured calls per scenario. Workspace open and ready
were measured once per workspace. Exact rows and error classifications are
in [the comparison CSV](2026-11-22-release-p95.csv).

| Suite / pinned subject | 4.0.1 units | 5.0.0 units | Comparable timing rows above +20% | 5.0.0 absolute harness |
| --- | ---: | ---: | ---: | --- |
| Fixtures | 3 / 3 / 1 | 3 / 3 / 1 | 11 / 64 | pass |
| FluentValidation `daa00b7` | 6 | 6 | 7 / 16 | required callers returned `SymbolNotFound` in both releases |
| Serilog `49b5339` | 19 | 19 | 8 / 17 | pass |
| Spectre.Console `0acc92f` | 29 | 29 | 7 / 17 | batch diagnostics p95 15.04 s against 15 s in 5.0.0 |
| Observables `6774626` | 223 | 293 | 7 / 17, changed graph size | ready and drift exceeded the absolute budgets |

Across matched non-error rows with the same loaded project counts, 33 of 114
exceeded +20%. Four additional same-count rows contain an error and two
are new scenarios. The reported p95 was 0.8 ms for `symbol_source` and 2.6 ms
for `symbol_resolve_at`. Small timing changes can cross a relative threshold
at this sample size, but `workspace_check_drift` grew by hundreds of
milliseconds on each of FluentValidation (649 → 967 ms), Serilog
(910 → 1,302 ms), and Spectre.Console (1,723 → 2,527 ms).

On Observables, open-to-ready grew from 25.4 s to 140.1 s while the loaded
graph grew by 70 units. The absolute 60 s ready target still failed. Treat
the relative difference there as a result for the whole open path and its
changed coverage. The p95 cap in #529 remains unmet.

## Drift follow-up on the 5.1 development branch

Re-ran `workspace_check_drift` against the same three OSS sources with
two warm-ups and nine measured calls per version. The candidate reused
canonical graph paths for read authorization. The current filesystem target
was still resolved and checked before file content was read.

| Subject | Baseline `ae59618` p95 | Candidate p95 | Change |
| --- | ---: | ---: | ---: |
| FluentValidation | 962 ms | 405 ms | −58% |
| Serilog | 1,159 ms | 479 ms | −59% |
| Spectre.Console | 2,194 ms | 793 ms | −64% |

An additional candidate run on Observables loaded all 293 units and put
drift p95 at 2.97 s, below its 5 s budget. This experiment measured only
drift. The full release comparison above describes the published 5.0.0 tag.

The FluentValidation callers failure came from the benchmark argument.
`symbol_members` returned the `ClassLevelCascadeMode` property first,
and `symbol_find_callers` requires a method handle. The suite now selects
a method or F# function. The corrected FluentValidation scenario passed
with a p95 of 32 ms over five measured calls. The tagged comparison
preserves the original error rows.

To repeat, build the benchmark at each release and run `--suite fixtures`
and `--suite scale --solution <path> --symbol <query>` with
`--iterations 5 --warmup 1`. Use the paths and queries in
[OSS results](oss-results.md). Save a separate JSON per subject and release,
then compare with
`python benches/compare_p95.py --pair <subject> <4.0.1.json> <5.0.0.json>`.
The operator's raw captures are under
`artifacts/release-p95-401-vs-500/{401,500}/`.

## Workspace open follow-up

Compared the previous development build (`3a28b09`) with #601
(`82f4529`) on the same Windows host and pinned subjects. Each pair
used the same working copy and alternated the run order. Existing subject
build outputs were kept. Each sample was a fresh benchmark process
running `--suite scale --filter workspace.open`.

| Subject | Loaded units on both builds | Baseline ready samples (s) | #601 ready samples (s) | Median change |
| --- | ---: | --- | --- | ---: |
| Observables `6774626` | 293 | 122.90, 127.39, 137.76 | 74.62, 75.31, 76.88 | −41% |
| Spectre.Console `0acc92f` | 29 | 11.91, 12.20, 12.63 | 7.74, 7.84, 7.85 | −36% |
| FluentValidation `daa00b7` | 6 | 3.83, 3.92, 3.96 | 3.17, 3.27, 3.34 | −17% |

`workspace_open` returned in under 76 ms in every run. The Observables
ready samples still exceeded the 60 s budget. A temporary profile on the
baseline counted 223 units in the native load and 293 after reconciliation,
with about 46 s in the extra MSBuild calls. Observables uses nested XML
folder elements, and the schema defines folders at the solution root.
Recovery of their projects still requires extra evaluations.
[SLNX schema](https://github.com/microsoft/vs-solutionpersistence/blob/main/src/Microsoft.VisualStudio.SolutionPersistence/Serializer/Xml/Slnx.xsd)

The #601 optimization avoids repeated path checks while preserving those
projects. The historical release cap in #529 remains unmet.

## Batch diagnostics follow-up

On the same Spectre.Console working copy, a profile found 28,285 compiler
diagnostics in the `Spectre.Console.Tests(net9.0)` project. A workspace batch
was sorting and projecting that full set on each 100-row inner page.
The batch now collects a Roslyn project's full results in one pass and
uses the existing workspace cursor to page the aggregate.

With one warm-up and five measured calls to
`--suite scale --filter project.diagnostics.batch`, p95 fell from
15,036 ms on `3a28b09` to 1,077 ms with the diagnostics change applied
in isolation. Both runs loaded 29 units and returned 50 rows and a
continuation cursor on the first page. This run passed the 15 s check.

## Windows path validation follow-up

On Observables, a profiled load on `1bc860c` spent 63.0 s in native
solution loading and project reconciliation. Building the snapshot,
checking its graph, replacing analyzer references, and starting file
watching then took 9.3 s. Using a single Windows metadata probe for
ordinary path components reduced the latter stages to 4.6 s in the
profiled candidate. Ready time was 72.4 s before and 69.3 s after, with
293 project units both times. Reparse points still go through link
resolution and an unresolvable target still fails path validation.

## First workspace acknowledgment follow-up

Replayed the pinned FluentValidation input against adjacent historical
commits. Its first open acknowledgment rose from a 42.43 ms median at
`46e6613` to 62.24 ms at `862b9c6`, where workspace sessions started
carrying the XAML usage index. The index pulled in the language adapters
and created an F# compiler checker during a C# workspace open.

The workspace tools now resolve without constructing the XAML language
services. The usage index resolves them when it processes XAML, and the
F# adapter creates its checker when it first needs compiler options or
semantic checking. A regression test exercises the workspace tools' DI
activation.

With three fresh processes per arm on the same pinned working copies,
the median first acknowledgment against `1bc860c` changed as follows.

| Subject | Before, ms | After, ms |
| --- | ---: | ---: |
| FluentValidation | 77.26 | 55.52 |
| Spectre.Console | 74.02 | 57.48 |

Both workspaces reached ready with their original project counts. The
improvement narrows the first-call difference from v4.0.1. The results
continue to exceed the +20% cap for this scenario.

## Nested SLNX recovery

On the pinned original Observables solution, instrumented serial recovery
opened 36 C# projects in 46.4 s and added 70 project units. Ten unsupported
shared-project entries accounted for about 11 ms. Each C# retry started
its own MSBuild host.

The batch uses a temporary traversal project with Roslyn's public
project loader. Its `SolutionDir` comes from the opened solution.
The workspace publishes only the recovered projects. Independent SDK
settings, an incomplete batch, and overlapping output paths continue
through the per-project recovery pass, which supplies the existing
unloaded-project warnings.

On one shared working copy of the original input, the serial build
reached ready at 70.2 s and the batch build at 34.6 s. The 293 project
units matched across project and metadata references, documents,
analyzers, output paths, and preprocessor symbols. Both runs emitted
the same 2,054 load warnings.
